# v0.5 considerations

Owner direction recorded 2026-11-05: keep the following related projects for
evaluation during v0.5 planning. This is an evaluation list, with no integration,
dependency, migration or replacement selected. Stable v0.4.0 implementation and
release acceptance remain the current priority.

## Related projects

The descriptions below summarize primary documentation reviewed on 2026-11-05.
They are not hands-on compatibility, performance or security results.

| Project | Documented focus | Evaluation for eef or eve |
| --- | --- | --- |
| [OpenClaw](https://docs.openclaw.ai/nodes) | Gateway, paired nodes, remote commands, local inference, camera/screen, voice and presence | Compare the complete assistant/node workflow; evaluate assistant and channel integration before duplicating it in eve |
| [OpenTela](https://github.com/eth-easl/OpenTela) | Decentralized compute discovery and model-serving routing using P2P networking and a CRDT registry | Evaluate optional inference integration and discovery/routing ideas |
| [HTCondor](https://htcondor.org/htcondor/overview/) | Batch jobs, resource matching, priorities and recovery | Compare scheduling, resource-owner policy and durable job lifecycle |
| [Kalavai](https://kalavai-net.github.io/kalavai-client/) | GPU pools and deployment of model-serving and AI workloads | Evaluate optional model-pool integration and setup requirements |
| [BOINC](https://boinc.berkeley.edu/) | Volunteer scientific computing on contributed consumer computers | Study heterogeneous resources, contribution controls and job lifecycle |
| [Ray](https://docs.ray.io/en/latest/ray-core/key-concepts.html) | Distributed tasks, stateful actors and resource-aware execution | Evaluate an optional compute backend for workloads that fit its execution model |

The overlap includes both assistant behavior and distributed node capabilities.
Gateway/node architecture, local models, media access and distributed scheduling
must not be presented as unique to eef or eve merely because their names differ.

## Evaluation questions

- Can the candidate reproduce an actual owner workflow across the two PCs, with
  understandable installation, permissions, diagnostics and recovery?
- What are the idle and active RAM, CPU, disk and network costs on those PCs?
  Include required services, containers, runtimes and model backends.
- Which existing components can be reused through supported interfaces, and what
  adapter, maintenance and licensing requirements would that introduce?
- How do cancellation, lost acknowledgements, disconnects, restart and retries
  behave? Repeating a compute task and repeating a device action require explicit
  treatment of effects and authorization.
- Can eef preserve node-owner controls, bounded resources and coordinator-approved
  execution while integrating the component?
- Does the integration improve the usable workflow enough to justify its cost
  compared with continuing the existing implementation?

Record the tested revision, configuration, hardware, observed results and remaining
gaps before making a selection. Consider contributing upstream or using an adapter
where suitable. This list does not commit eef to adopting a different coordination
model, adding all six systems, or shipping any integration in v0.5.

The [command-first core roadmap](ROADMAP-CORE.md) remains the active implementation
plan. Public eve is currently at the design/documentation stage; this review does
not establish a working eve integration or a performance advantage for eef.
